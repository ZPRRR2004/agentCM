# 谓词定义协议 v1

此页保留历史协议。2026-10-21 起新实验采用 [v2 三类节点协议](predicate-definition-v2.md)。

协议标识为 `predicate-definition/v1`。2026-10-14 更新发现与审核 Prompt 的粒度策略：`predicate-granularity/v1`。当前流程输出带类型参数的谓词定义。

## 要解决的问题

旧关系类型固定为名称、定义、源描述、目标描述，容易把关系限制在两个端点。现在用有序参数表达一个可判断是否成立的断言，支持身份属性、信息使用、带作用域的替代和多前提推导。

例如，`IS_PLAN(action)` 描述一个对象，`USES_AS_INPUT(action, information)` 描述信息如何供应行动的输入，`SUPERSEDES(new_information, old_information, scope)` 显式保留替代的适用范围。这些示例用于校准表达方式，实际词表由轨迹发现与审核形成。

## 五个字段

```json
{
  "name": "USES_AS_INPUT",
  "definition": "行动将指定信息提供的可定位值或数据内容作为操作输入。",
  "parameters": [
    {"name": "action", "type": "action", "description": "接收输入的行动。"},
    {"name": "information", "type": "information", "description": "提供输入值或数据内容的信息。"}
  ],
  "assertion_conditions": [
    "详细轨迹能够定位这项信息及接收它的行动。",
    "行动的参数值或数据输入可追溯到这项信息。"
  ],
  "exclusion_conditions": [
    "信息仅用于选择行动、且没有提供行动输入时，不满足此谓词。",
    "时间相邻或主题相同，且没有可观察的输入联系时，不满足此谓词。"
  ]
}
```

| 字段 | 约束 |
| --- | --- |
| `name` | 大写符号名；字母、数字和下划线；Registry 内唯一 |
| `definition` | 非空定义，明确参数角色之间的断言 |
| `parameters` | 非空有序列表；每项仅含 name/type/description；参数名唯一 |
| `assertion_conditions` | 至少一个非空条件；描述成立所需证据和上下文 |
| `exclusion_conditions` | 非空字符串组成的列表；允许空列表；描述近似但不成立的情形 |

参数顺序决定位置，交换两个参数可能改变断言。当前不支持零元谓词。条件是供抽取和审核使用的自然语言约定，后续才能转成可执行规则。

## 参数对象类型

| 类型 | 含义 |
| --- | --- |
| `action` | 可定位的行动、显式消息或决策；允许计划与约束消息 |
| `information` | 可定位的事实、观测内容、结论、计划或约束内容 |
| `goal` | 用户任务或明确的局部目标 |
| `artifact` | 文件、资源或产出对象 |
| `scope` | 断言适用的时间、任务或环境范围 |
| `rule` | 可识别的推导规则或操作 |

允许添加一个 `[]` 后缀表示该类对象的集合，例如 `information[]`；不允许嵌套集合或临时添加对象类型。集合的具体 ID、顺序及去重策略留给实例协议确定。

这些类型是第一版实现选择，需要 review。`action` 中的计划消息与 `information` 中的计划内容可以有不同身份，之后由实例层明确绑定，不能仅凭类型名称视为同一对象。

## 流程与边界

```text
窗口 → 独立发现 → existing/new/uncertain 比较 → 审核 → Registry
                                                      ↓
                                    每批人工反馈 → 修改计划 → Registry
```

- 比较时，`new/uncertain` 原样保留候选；`existing` 要求语义双向等价、有序参数类型一致。精确机制被宽泛概念包含时，按独立的新定义处理；过粗或语义边界模糊的候选交给 `uncertain`。空 Registry 的候选全部归入 `new`，再由 Review 校准粒度。
- 审核依据窗口证据细化过粗候选、归纳过细候选。每个拆出的机制分别需要证据；修订已有定义保持语义身份，每次修订保留前后内容。
- `MERGE` 要求源定义与最终保留定义语义双向等价。代码检查有序参数类型，Prompt 指导模型比较机制、角色、条件和作用域。上位概念包含、类型签名相同、样例重合均不构成合并依据。
- 不从“时间先后”“主题相似”直接推断实际使用、因果或修复成功。
- 离线可使用前后摘要辅助发现；具体事实需要原始证据，在线实例抽取只能看当前前缀。
- 当前 Registry 保存定义列表，运行状态保存协议版本；旧关系类型状态拒绝恢复，历史产物原样保留。

## 粒度标准与校准方式

粒度按“可区分的语义机制”确定：相同机制和适用条件跨工具、资源泛化；机制、参数角色、成立条件或必要作用域变化时保留区别。

| 对照 | 处理 |
| --- | --- |
| 路径、数据库 ID、URL 分别供应命令输入 | 共用 `USES_AS_INPUT`，资源差异放入参数 |
| 信息供应输入、指导选择、充当验收标准 | 分别表达具体机制，避免泛化成一个 `USES` |
| 诊断、尝试修复、检查修复、确认成功 | 依据各自的证据和成功条件区分 |
| 同一阈值传入检查器并作为验收标准 | 允许多个谓词同时成立，每项各有证据 |
| 精确谓词被宽泛谓词包含 | 保留精确谓词，包含关系与等价关系分别判断 |

提示词要求进行两种校准：替换资源或工具后，机制是否相同；对齐角色后，能否构造一个使两个定义判断不同的边界情形。后一种情形用于检查定义差异，实际抽取仍依据窗口中的证据。

`USES` 等名称可用于概念分组。当前 JSON 输出保持五字段的具体谓词定义列表。人工反馈的操作为 KEEP / DELETE / REVISE / MERGE；拆分宽泛定义由带轨迹证据的发现和审核阶段处理。

规则源文件为 [共享粒度 Prompt](../src/discover_predicates/prompts/common/granularity_examples.txt)，由加载器附加到四个阶段的 system 消息。完整改动见 [2026-10-14 Prompt 改动记录](2026-10-14-granularity-prompt-update.md)。
