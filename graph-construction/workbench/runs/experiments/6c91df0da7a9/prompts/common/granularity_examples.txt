# Predicate Definition Contract: predicate-definition/v2

## 1. Definition Format and Node Contract

A predicate is a reusable Boolean assertion over an ordered list of typed arguments.

Each predicate definition must contain exactly five fields:

- `name`: A unique UPPER_SNAKE_CASE predicate name.
- `definition`: A precise statement of its semantic meaning.
- `parameters`: A nonempty ordered list of `{name, type, description}` with unique parameter names.
- `assertion_conditions`: Observable conditions required for the predicate to hold. Must be nonempty.
- `exclusion_conditions`: Cases where the predicate's distinguishing requirements are not satisfied. May be empty.

Allowed parameter types are `action`, `observation`, `reasoning`, and their homogeneous collections (`action[]`, `observation[]`, `reasoning[]`).

- `action`: A recorded tool invocation.
- `observation`: A recorded tool result.
- `reasoning`: Recorded agent text, including plans, hypotheses, decisions, and conclusions.

All parameters must refer to actual graph nodes. Resources, goals, constraints, and other abstract concepts must be represented through node content rather than additional parameter types.

Preserve parameter roles and ordering. Structural call-result relationships are already provided and must not be rediscovered as semantic predicates.

## 2. Granularity Rules

### Core Objective

Discover **reusable, task-independent logical and semantic mechanisms underlying agent behavior**.

Prioritize mechanisms explaining how information, evidence, assumptions, constraints, decisions, actions, and outcomes interact.

Focus on the logical or functional role of nodes and their relationships, rather than merely describing concrete operations.

A predicate should remain meaningful when the task domain, tool, resource, or implementation changes while the underlying mechanism remains the same.

Determine predicate arity from the semantic roles necessary to express the mechanism.

### Unary Predicates — Semantic Roles of Individual Nodes

A unary predicate identifies a meaningful property or role of one node.

- Prioritize reusable roles such as planning, hypothesizing, diagnosing, evaluating, deciding, and concluding.
- Describe what the node semantically represents or accomplishes.
- Avoid predicates that merely label specific commands, tools, resources, or task procedures.
- Do not impose incidental restrictions on how a semantic role is expressed.

### Binary Predicates — Logical Relationships Between Nodes

A binary predicate describes a distinguishable mechanism connecting two nodes.

- Identify what each argument contributes to the relationship.
- Prioritize information flow, evidential support, constraints, decision guidance, derivation, correction, and functional dependencies.
- Distinguish mechanisms by their semantic roles and truth conditions.
- Generalize across concrete operations when the underlying relationship is unchanged.
- Require identifiable evidence of the relationship; temporal adjacency or topical similarity alone is insufficient.

### Ternary and Higher-Arity Predicates — Joint Logical Relationships

A multi-argument predicate represents a mechanism requiring three or more semantic roles.

- Include only arguments essential to the complete assertion.
- Prioritize joint evidence, hypothesis testing, conflict resolution, constrained decisions, and outcome verification when supported.
- Preserve joint dependencies that cannot be fully expressed by independent lower-arity predicates.
- Use separate lower-arity predicates when relationships are independently meaningful.
- Use homogeneous collection parameters when multiple nodes jointly fill one semantic role. Specify whether support is collective or alternative.

### General Granularity Principles

1. **Mechanism over Operation:** Prefer reusable logical or functional mechanisms over task-specific operational descriptions.
2. **Essential vs. Incidental:** Preserve essential semantic conditions; generalize tools, resources, quantities, and implementation details that do not change the mechanism.
3. **Distinguishability:** Keep predicates separate when a meaningful case can satisfy one but not the other.
4. **Non-exclusivity:** Multiple predicates may hold over the same nodes. A more specific predicate is justified when it captures an additional meaningful semantic distinction, not merely an implementation detail.
5. **Evidence:** Define predicates using identifiable trajectory evidence. Assertion and exclusion conditions must reflect the predicate's actual semantic requirements.
6. **Outcome:** Distinguish intentions, attempts, checks, and confirmed outcomes. Do not infer success from an attempted operation or an executed check alone.

Do not create separate predicates for superficial variations of the same mechanism. Do not replace identifiable mechanisms with generic relations such as `USES`, `RELATED_TO`, or `DEPENDS_ON`.

Do not force any predicate count or arity distribution. Let the trajectory determine the vocabulary.

## 3. Granularity Examples

### Example 1 — Unary: Planning Intent

**Scenario:** A reasoning node states, "I will inspect the configuration before making changes."

```json
{
  "name": "IS_PLAN",
  "definition": "The reasoning explicitly expresses an intended future action or sequence of actions.",
  "parameters": [
    {
      "name": "reasoning",
      "type": "reasoning",
      "description": "The agent text expressing the intended action or plan."
    }
  ],
  "assertion_conditions": [
    "The reasoning explicitly identifies at least one intended future action."
  ],
  "exclusion_conditions": [
    "The reasoning only reports completed actions without expressing a future intention."
  ]
}
```

**Granularity lesson:** Capture the semantic role of planning, independent of the specific operation, task, or number of planned steps.

### Example 2 — Binary: Evidential Support

**Scenario:**

Observation: "The available dataset contains only 120 samples."

Reasoning: "The dataset is too small for the proposed training setup."

```json
{
  "name": "GROUNDS_CONCLUSION_IN_OBSERVATION",
  "definition": "The reasoning draws a conclusion using identifiable information from the observation as supporting evidence.",
  "parameters": [
    {
      "name": "reasoning",
      "type": "reasoning",
      "description": "The reasoning expressing the evidence-based conclusion."
    },
    {
      "name": "observation",
      "type": "observation",
      "description": "The observation supplying evidence for that conclusion."
    }
  ],
  "assertion_conditions": [
    "The reasoning states a conclusion supported by identifiable content from the observation.",
    "The observation contributes evidential support to the stated conclusion."
  ],
  "exclusion_conditions": [
    "The reasoning merely repeats the observation without drawing a conclusion.",
    "The observation is unrelated to the conclusion or provides no identifiable support."
  ]
}
```

**Granularity lesson:** Capture the evidential relationship between nodes. This mechanism generalizes across datasets, experiments, diagnostics, and other domains. Supplying evidence for a conclusion is distinguishable from supplying an operational input to an action.

### Example 3 — Ternary: Hypothesis Testing

**Scenario:**

Reasoning: "I need to determine whether the service is reachable."

Action: Send an HTTP request to the service endpoint.

Observation: "HTTP 200 OK."

```json
{
  "name": "TESTS_ASSUMPTION_WITH_PROBE",
  "definition": "A targeted action tests an assumption or uncertainty identified in reasoning, and its observed result provides evidence for resolving that uncertainty.",
  "parameters": [
    {
      "name": "probe_action",
      "type": "action",
      "description": "The action performing the targeted test."
    },
    {
      "name": "assumption_reasoning",
      "type": "reasoning",
      "description": "The reasoning identifying the assumption or uncertainty being tested."
    },
    {
      "name": "probe_result",
      "type": "observation",
      "description": "The observation reporting the result relevant to the assumption."
    }
  ],
  "assertion_conditions": [
    "The reasoning identifies a specific assumption or uncertainty.",
    "The action is directed at testing that assumption.",
    "The resulting observation provides interpretable evidence about the assumption."
  ],
  "exclusion_conditions": [
    "The action is unrelated to the stated assumption.",
    "The observation does not address the assumption being tested.",
    "No identifiable assumption or uncertainty motivates the test."
  ]
}
```

**Granularity lesson:** The three arguments jointly represent a hypothesis-testing mechanism. The action-result relationship alone cannot capture which assumption was tested.

These examples illustrate semantic abstraction and argument structure. They do not prescribe a fixed predicate vocabulary or restrict the discovery of other supported mechanisms.
